# API v2 — el motor, servido

Contrato de solo lectura, implementado en [`app/api/src/v2/`](../../app/api/src/v2/).

**La API no calcula finanzas.** Todo lo que devuelve lo precalculó el motor de
[`core/`](../../core/) y lo publicó en MotherDuck: score, pilares, señales, drivers, régimen,
outlook, alertas, narrativas, grupos y frames. Aquí solo se lee, se filtra, se ordena y se
pagina. Cómo se calcula lo que sirve: [`../engine.md`](../engine.md).

---

## 1. De dónde salen los datos

Origen: **MotherDuck**, base `hackspain_2026`, esquema `main`.

| Variable | Por defecto | Para qué |
|---|---|---|
| `MOTHERDUCK_TOKEN` | — (**obligatoria**) | credencial; se lee de `app/api/.env` |
| `MOTHERDUCK_DATABASE` | `md:hackspain_2026?saas_mode=true` | apuntar a otra base o a un `.duckdb` local |
| `PORT` | `8787` | puerto del servidor |

```bash
cd app && corepack pnpm --filter api dev
```

**Sin conexión, todos los `/api/v2/*` responden `503`** con
`{ status: "source_unavailable", source: "motherduck" }`. No se sirven fixtures en su lugar:
una pantalla vacía es preferible a un número inventado.

> MotherDuck limita las conexiones por token. Con varias APIs abiertas a la vez, las nuevas
> devuelven `503` mientras las viejas siguen sirviendo.

CORS acepta `http://localhost:5173` y `:4173`.

### `/health`

```jsonc
{ "status": "ok", "contract_version": "dashboard-v1", "dataset_version": "embat-v2",
  "cutoff_date": "2026-08-01", "source": "motherduck", "data_kind": "real",
  "engine": "embat-layered-v1",
  "v2": { "model_version": "embat-layered-v1", "params_version": "sha256:c463221d…",
          "cutoff_date": "2026-08-01", "months": 24, "snapshots_only": false } }
```

`model_version` y `params_version` salen del manifiesto publicado, nunca están escritos en el
código: si el motor republica con otros parámetros, la API lo refleja sola.

## 2. Reglas transversales

- Todos los endpoints son `GET` y devuelven JSON.
- `as_of` por defecto = **último mes disponible** (`2026-08`). Debe existir en el dataset.
- Validación de dominio cerrado → `400 {error:"invalid_query", message}` diciendo qué
  valores valen. Ej.: `sort inválido: ebitda. Válidos: score, delta_1m, delta_3m`.
- Id mal formado → `400 {error:"invalid_company_id"|"invalid_group_id", message}`.
- Entidad inexistente → `404 {error:"company_not_found"|"group_not_found"|"frame_not_found"|"month_not_found", message}`.
- Sin tablas v2 → `503 {status:"no_v2_tables", message, hint}` (mismo patrón que
  `sendNoExports` de v1).
- `limit` entre 1 y **500** (defecto 50); `offset` ≥ 0 (defecto 0).

Dominios cerrados:

| Parámetro | Valores |
|---|---|
| `unit` | `company`, `group` |
| `sort` (universe) | `score`, `delta_1m`, `delta_3m` |
| `order` | `asc`, `desc` |
| `band` | `solid`, `healthy`, `watch`, `stress` |
| `regime` | `warmup`, `stable`, `improving`, `deteriorating`, `blip`, `shock_pending`, `recovering` |
| `pillar` | `L`, `P`, `C`, `D`, `A` |
| `group_by` | `group`, `country`, `erp` |
| `metric` | `delta_3m`, `delta_1m`, `score` |
| `size_by` | `op_in_12m`, `n_companies` |
| `severity` | `watch`, `review`, `urgent` |
| `direction` | `down`, `up` |
| `as_of`, `month` | `YYYY-MM` **existente** en el dataset |
| `from`, `to`, `since`, `until` | `YYYY-MM` (solo formato; recortan, no fallan si caen fuera) |

### Los ejemplos: qué son y cómo leer el recorte

`docs/api/examples/*.json` son respuestas **reales del dataset completo**, escritas por el
script de §6 y nunca a mano (recortarlas a mano es justo lo que las dejó desfasadas del
dataset). Convención del recorte:

- Todo array de más de tres elementos se recorta a **los tres primeros**, salvo
  `sparkline_12`, `months`, `anchors`, `strength_flags`, `countries` y `currencies`, que van
  enteros porque su longitud *es* el dato.
- Cada recorte deja marca: una clave hermana **`_truncated`** en el mismo objeto, con la
  longitud real del array en la respuesta. Así, `{"items": [3 alertas], "_truncated":
  {"items": 50}, "total": 839}` se lee «la respuesta traía los 50 items de la página por
  defecto, de 839 en total; aquí ves 3».
- `/companies/:id/timeline` responde un array plano, y un array no admite clave hermana: ahí
  la marca va como **último elemento**, `{"_truncated": {"_root": 21}}`.
- `_truncated` **no existe en la API**: es del ejemplo. Las claves van ordenadas
  alfabéticamente para que el fichero sea estable byte a byte, así que el orden de un
  ejemplo no es el de la respuesta real (que tampoco es contrato: es JSON).

## 3. Endpoints

### `GET /api/v2/universe`

El universo en un mes: una fila por empresa (o por grupo) con score, delta, régimen y
sparkline. Es la tabla principal de la UI.

| Parámetro | Dominio | Defecto |
|---|---|---|
| `as_of` | mes del dataset | último mes |
| `unit` | `company` \| `group` | `company` |
| `sort` | `score` \| `delta_1m` \| `delta_3m` | `score` |
| `order` | `asc` \| `desc` | `desc` |
| `band`, `regime` | dominio cerrado | sin filtro |
| `q` | texto libre (id o nombre, sin distinguir mayúsculas) | sin filtro |
| `group_id` | `GROUP_\d{4}` | sin filtro |
| `limit`, `offset` | 1–500 / ≥ 0 | 50 / 0 |

Errores: `400` por cualquier parámetro fuera de dominio; `503` sin tablas.

```jsonc
{ "items": [ { "id": "COMP_0999", "name": "Transportes Duero S.L.U.", "group_id": "GROUP_0222",
    "group_name": "Beltran Participaciones", "score": 97.39, "band": "solid", "delta_1m": 1.59, "delta_3m": 9.16, "regime": "stable",
    "outlook_label": "positive", "confidence": 0.81, "branch": "no_debt",
    "op_in_12m": 1485894.83, "sparkline_12": [ /* 12 meses hasta as_of */ ], "alert": false } ],
  "total": 1286, "as_of": "2026-08", "unit": "company", "limit": 50, "offset": 0,
  "data_kind": "mock" }
```

- `sparkline_12`: los 12 últimos meses **hasta `as_of`**; menos puntos si la empresa tiene
  menos historia (una empresa que arranca en 2026-01 trae 8).
- `alert`: hay alerta detectada en `as_of` para esa entidad.
- `group_name`: el nombre del grupo (`groups.csv`) viaja con la empresa para que el
  buscador, el Mapa y las alertas no lo resuelvan aparte; `null` si el grupo no existe.
  Las filiales de `/groups/:id` son el mismo resumen y también lo llevan.
- Con `unit=group` los items cambian: `group_id: null`, `group_name: null`, `op_in_12m_eur`,
  `n_companies_scored`, `dispersion`, `weakest_company` y `outlook_label: null`
  (`group_timeline.csv` no publica etiqueta de outlook).

Ejemplo completo: [`examples/universe.json`](examples/universe.json).

### `GET /api/v2/companies/:id`

El vector completo de una empresa en `as_of`.

| Parámetro | Dominio | Defecto |
|---|---|---|
| `:id` | `COMP_\d{4}` | — |
| `as_of` | mes del dataset | último mes |

Errores: `400 invalid_company_id`; `404 company_not_found`; `404 month_not_found` si la
empresa existe pero no estaba activa en `as_of`; `503` sin tablas.

```jsonc
{ "company": { /* fila de companies.csv: identificación, cobertura real, op_in_12m */ },
  "as_of": "2026-08", "score": 57.42, "band": "watch",
  "delta_1m": 1.11, "delta_3m": -1.29, "delta_6m": -6.82,
  "regime": "deteriorating", "confidence": 1, "branch": "full", "warmup": false,
  "base": 64.40,
  "outlook": {"h3": 53.75, "h6": 50.83, "low": 41.42, "high": 60.23, "label": "negative"},
  "pillars": {"L": {"value": 0.41, "weight": 0.25}, "P": {…}, "C": {…}, "D": {…}, "A": {…}},
  "strength_flags": [],
  "timeline": [{"month": "2024-12", "score": 65.15, "band": "healthy", "regime": "warmup",
                "outlook_low": 55.75, "outlook_high": 74.56}],
  "drivers": [{"rank": 1, "signal_id": "L1", "pillar": "L", "contribution": -2.95,
               "delta_vs_prev": 0.01, "value": 7.66,
               "value_fmt": "8 dias de colchon de caja", "direction": "neutral"}],
  "penalty": {"points": 1.99, "weakest_pillar": "L"},
  "cap": null,
  "alert": { /* fila de alerts.csv, o null */ },
  "narrative": {"headline": "…", "body": "…", "watch_next": "…", "guardrail_passed": true},
  "audit": {"data_kind": "mock", "params_version": "v1", "model_version": "mock-v1",
            "data_version": "embat-v2", "generator_version": "mock-gen-1", "seed": 42,
            "generated_at": "2026-09-19T00:00:00+00:00"} }
```

- `timeline` trae **todos** los meses activos de la empresa (no solo hasta `as_of`).
- `base`: la parte del score que explica la empresa mediana del universo
  (`100 · Σ weight · u_ref` sobre las señales disponibles, así que varía con la cobertura
  de cada empresa; `reference.base_median` de `/meta` es su mediana). Identidad:
  `score = base + Σ contribution − penalty − (level − score cuando hay techo)`, con las
  `contribution` de `/companies/:id/signals` en `as_of`.
- `cap`: `null` cuando no hay techo; `{code, value}` cuando sí (`LOCFULL`, `NEGCASH`,
  `SSMISS`, `DEBTSTOP`).
- `penalty.points` es **positivo** (puntos restados, como en `score_timeline.csv`) y
  `weakest_pillar` es `null` cuando no hay penalización.
- `alert` es la última alerta con `month_detected <= as_of`, o `null`.
- `drivers` incluye las filas `PENALTY` y `CAP` de `drivers.csv` cuando existen.

Ejemplo completo: [`examples/company.json`](examples/company.json).

### `GET /api/v2/companies/:id/signals`

Las 28 señales agrupadas por pilar, con su serie histórica.

| Parámetro | Dominio | Defecto |
|---|---|---|
| `as_of` | mes del dataset | último mes |
| `pillar` | `L` \| `P` \| `C` \| `D` \| `A` | los cinco |

Errores: `400 invalid_company_id`, `400 invalid_query` (pillar/as_of), `404
company_not_found`, `404 month_not_found`, `503`.

```jsonc
{ "company_id": "COMP_0075", "as_of": "2026-08",
  "pillars": [ { "pillar": "L", "pillar_name": "Liquidez", "weight": 0.35, "value": 0.58,
    "signals": [ { "signal_id": "L1", "name": "Dias de colchon de caja", "unit": "dias",
      "value": 31.51, "value_fmt": "32 dias de colchon de caja", "u": 0.64, "u_smooth": 0.64,
      "u_ref": 0.62, "weight": 0.1042, "contribution": 0.2, "delta_vs_prev": -0.001,
      "is_available": true, "quality_flag": null,
      "series_24m": [{"month": "2024-09", "value": 26.12,
                      "value_fmt": "26 dias de colchon de caja", "u": 0.58, "u_smooth": 0.58,
                      "weight": 0.1042, "contribution": -0.4, "delta_vs_prev": 0,
                      "is_available": true}] } ] },
    { "pillar": "P", "pillar_name": "Disciplina de pago propia", "weight": 0.0972,
      "value": 0.7,
      "signals": [ { "signal_id": "P1", "name": "Facturas propias pagadas tarde",
        "value": null, "value_fmt": null, "u": null, "u_smooth": null, "u_ref": null,
        "weight": 0, "contribution": 0, "delta_vs_prev": 0, "is_available": false,
        "quality_flag": null, "series_24m": [ /* … */ ] } ] } ] }
```

- `series_24m`: todos los meses **hasta `as_of`** (24 como máximo; menos si la empresa
  tiene menos historia). Cada punto lleva lo que `signals.csv` ya trae para ese mes:
  `month`, `value`, `value_fmt`, `u`, `u_smooth`, `weight`, `contribution`, `delta_vs_prev`
  e `is_available` (en una señal no disponible: `value`, `value_fmt`, `u` y `u_smooth` a
  `null`, `weight`, `contribution` y `delta_vs_prev` a 0). `quality_flag` no viaja en la
  serie: es del mes de corte. `u_ref` tampoco: es una constante por señal.
- Vienen **las 28 señales que puntúan**, también las que la empresa no puede tener: llegan
  con `is_available: false`, sin `value` ni `u` y con `weight: 0`. Es la diferencia que la
  UI tiene que pintar: *no aplica* (`is_available: false`) no es *falta el dato*. Una
  empresa sin línea de crédito trae `D1` no disponible; una sin facturas, `P1…P3` y
  `C1…C6`.
- El peso se renormaliza sobre lo disponible: en el ejemplo (`COMP_0075`, sin facturas) `L`
  pesa 0,35 en vez de 0,25, `P` baja a 0,097 (solo puntúan `P4…P6`) y `C`, con sus seis
  señales no disponibles, se queda en `weight: 0` y `value: null`.
- `weight` es el peso efectivo de la señal en el score total (pilar × señal renormalizado);
  `contribution` son puntos: `100 · weight · (u_smooth − u_ref)`.

Ejemplo completo: [`examples/company-signals.json`](examples/company-signals.json) — es
`COMP_0075`, no `COMP_1267`, a propósito: `COMP_1267` tiene cobertura completa y sus 28
señales están disponibles, así que no enseña el caso `is_available: false`.

### `GET /api/v2/companies/:id/timeline`

La serie mensual completa, con nivel, penalización, techo y banda de outlook. Devuelve un
**array plano** (sin envoltorio).

| Parámetro | Dominio | Defecto |
|---|---|---|
| `from`, `to` | `YYYY-MM` | toda la historia activa |

Errores: `400 invalid_company_id`, `400 invalid_query` (from/to mal formados), `404
company_not_found`, `503`.

```jsonc
[ {"month": "2024-12", "score": 65.15, "level": 65.15, "penalty": 0, "cap": 100,
   "cap_code": null, "band": "healthy", "regime": "warmup", "delta_1m": null,
   "outlook_3m": 65.15, "outlook_6m": 65.15, "outlook_low": 55.75, "outlook_high": 74.56,
   "confidence": 0.4, "base": 64.40,
   "pillars": {"L": {"value": 0.28, "weight": 0.25}, "P": {"value": 0.46, "weight": 0.2},
               "C": {"value": null, "weight": 0}, "D": {"value": 0.62, "weight": 0.2},
               "A": {"value": 0.44, "weight": 0.2}}} ]
```

`pillars` es el mismo objeto que en `/companies/:id`, mes a mes, para que la gráfica por
familia pinte cada pilar sin una consulta por mes. `value` es P_k en 0–1; la UI lo muestra
×100 en pts. Un pilar sin datos va como `value: null` con `weight: 0`: nunca se imputa 0.

`cap` es 100 cuando no hay techo; cuando lo hay, `cap` baja (p. ej. 60 con
`cap_code: "LOCFULL"`) y `score = min(level, cap)`. `base` es el mismo de
`/companies/:id` (la parte del score que explica la empresa mediana) y cumple en cada mes
`score = base + Σ contribution − penalty − (level − score cuando hay techo)`; `level` ya
lleva la penalización restada (`level = Σ w·P − penalty`, [`../engine.md`](../engine.md) §1
§4), así que sin techo `score = level`.

Ejemplo completo: [`examples/company-timeline.json`](examples/company-timeline.json).

### `GET /api/v2/companies/:id/report` — Informe de Health

Informe en prosa **pregenerado fuera del loop** con Claude por
`app/tools/gen_health_reports.py` (ver `app/tools/README.md`) y versionado en
`app/api/data/reports/<company_id>.json`. La API lo sirve tal cual está en disco: no lo
recalcula, no lo reescribe y no llama a ningún modelo en vivo.

| Variable | Valor por defecto | Para qué |
|---|---|---|
| `XRAY_REPORTS_DIR` | `app/api/data/reports` | directorio de los JSON pregenerados |

Errores: `400 invalid_company_id`, `404 company_not_found` (la empresa no está en el
dataset), `404 report_not_found` con `message: "Informe no disponible para esta empresa"`
(la empresa existe pero no tiene fichero), `500` si el fichero no es JSON válido, `503` sin
tablas.

```jsonc
{ "company_id": "COMP_0009", "as_of": "2026-08", "generated_at": "2026-09-19T10:00:00Z",
  "model": "claude-opus-5", "risk_level": "low",
  "summary": "Suministros Doriga S.L.U. cierra agosto de 2026 en banda sólida…",
  "sections": [ {"title": "Resumen", "body": "…"}, {"title": "Liquidez y caja", "body": "…"},
                {"title": "Pagos y cobros", "body": "…"}, {"title": "Deuda", "body": "…"},
                {"title": "Actividad", "body": "…"} ],
  "watch_next": ["…", "…"] }
```

- `risk_level` ∈ `low` | `medium` | `high`; `sections` lleva siempre esos cinco títulos en
  ese orden; `watch_next` tiene entre 2 y 4 puntos.
- Solo cita cifras que ya vienen en `value_fmt` de señales y drivers: la regla «sin cifras
  inventadas» se impone en el prompt y se valida con `pydantic` antes de escribir el fichero.

Ejemplo completo: [`examples/company-report.json`](examples/company-report.json) (se genera
cuando existe `app/api/data/reports/COMP_0004.json`; fixture de test en
`app/api/test/fixtures/v2/reports/COMP_0009.json`).

### `GET /api/v2/treemap`

Agregación por grupo, país o ERP para el treemap: tamaño y color por empresa, y el color
del bucket ya resuelto en el servidor.

| Parámetro | Dominio | Defecto |
|---|---|---|
| `as_of` | mes del dataset | último mes |
| `group_by` | `group` \| `country` \| `erp` | `group` |
| `metric` | `delta_3m` \| `delta_1m` \| `score` | `delta_3m` |
| `size_by` | `op_in_12m` \| `n_companies` | `op_in_12m` |

```jsonc
{ "as_of": "2026-08", "group_by": "group", "metric": "delta_3m", "size_by": "op_in_12m",
  "delta_source": "group_timeline",
  "groups": [ { "key": "GROUP_0126", "label": "Bierzo Holding", "value_sum": 28890006406.22,
    "delta": 1.32,
    "coverage": {"items_with_metric": 11, "items_total": 11,
                 "size_with_metric": 28890006406.22},
    "items": [ {"id": "COMP_1185", "name": "Comercial Navarro y Cia. S.L.",
                "size": 28775890156, "color_value": 1.32, "score": 57.78,
                "band": "watch"} ] } ] }
```

- `value_sum` = suma de `size` de **todos** los items: es el área del rectángulo, no la
  cobertura. Con `group_by=country|erp`, las empresas sin país o sin ERP caen en la clave
  `unknown`.
- `delta` = el color del bucket, y es **`null` cuando no hay dato**; nunca 0 imputado. Un
  bucket sin métrica hay que pintarlo como «sin dato», no como «delta exactamente 0»
  (regla dura del contrato: «Ausencia de datos ≠ 0»,
  contrato `dashboard-v1` §3). Se ve sobre todo en replay: en los tres
  primeros meses del dataset ninguna empresa tiene `delta_3m` todavía, así que
  `GET /api/v2/treemap?as_of=2024-10` devuelve todos los buckets con `delta: null`.
- `delta_source` dice de dónde sale ese `delta` y depende solo de `group_by`:
  - `group_timeline` (`group_by=group`): el valor **precalculado** del grupo en
    `group_timeline.csv`, el mismo que devuelven `/api/v2/groups/:id` y
    `/api/v2/universe?unit=group`. La API no lo recalcula (§1 del contrato: «la API no
    calcula finanzas»), así que el treemap y la ficha del grupo no se contradicen y el peso
    es el `op_in_12m_eur` del pipeline, sin mezclar divisas. Consecuencia: con
    `group_by=group`, `size_by` cambia el **tamaño** del rectángulo pero no el color.
  - `weighted_mean` (`group_by=country|erp`): no hay fila precalculada para esos cortes, así
    que la API agrega los items del bucket: media de `metric` ponderada por `size` **solo
    sobre los items con métrica** (los `color_value: null` quedan fuera del numerador y del
    denominador). Sin ningún item con métrica, `delta: null`. Si los que la tienen suman
    peso 0 (todos con `op_in_12m = 0`), sale la media simple, la misma salida de emergencia
    que usa la consolidación de grupo del pipeline.
- `coverage` describe siempre los **items** del bucket, sea cual sea `delta_source`:
  `items_with_metric` de `items_total` empresas tienen `color_value != null`, y
  `size_with_metric` es el `size` que suman esas empresas (el denominador real de
  `weighted_mean`). `size_with_metric < value_sum` significa que hay área pintada que no
  respalda el color.
- **Cuidado**: `op_in_12m` está en la **moneda contable de cada empresa** (`companies.csv`),
  así que `size`, `value_sum` y `size_with_metric` mezclan divisas. Para comparar grupos en
  EUR está `op_in_12m_eur` en `/api/v2/universe?unit=group`.

Ejemplo completo: [`examples/treemap.json`](examples/treemap.json).

## 4. Desviaciones respecto al contrato de diseño

| Qué | Decisión |
|---|---|
| El diseño llamaba `signal` al campo del driver | v2 usa **`signal_id`** en todos los endpoints (drivers, señales, catálogo, alertas) para no tener dos nombres del mismo campo |
| El diseño ponía `penalty: {weakest_pillar, points: -7.5}` | `points` se sirve con el signo de `score_timeline.csv` (**positivo** = puntos restados) y `weakest_pillar` es el pilar con la nota más baja, `null` si no hay penalización |
| PLAN pide `cap` a secas | `cap` es `null` o `{code, value}`; en `/timeline` van las dos columnas crudas (`cap`, `cap_code`) |
| PLAN pide `{items, total}` en alerts | se añaden `limit` y `offset` (misma forma que v1) |
| PLAN pide `sort` en universe | `sort` ordena; `unit=group` usa la misma clave sobre `group_timeline.csv` |
| `/universe`, `/signals` | se añaden campos que ya están en las tablas y la UI va a pedir: `branch`, `op_in_12m`/`op_in_12m_eur`, `u_ref`, `weight`, `unit`, `pillar_name` |
| `/companies/:id`, `/timeline` | se añade `base` (columna de `score_timeline.csv`) para que la UI pueda enseñar la identidad `base + Σ contribution − penalty` |
| `/meta` → `params` | no hay fichero de parámetros exportado: se congelan en `src/v2/params.ts` desde `catalog.py` (y los tramos de confianza de `core.py`) |
| `reports` | `/companies/:id/report` no sale de las tablas del mock: son ficheros JSON pregenerados fuera del loop; ver `app/tools/README.md` |

## 5. Campos que la publicación todavía no trae

Nombres exactos, para que el motor real o una siguiente pasada del generador los añadan:

- `coverage_ratio` en los items de `/universe` y en las filiales de `/groups/:id`. Existe
  en `exports/v1/results/<id>.json` (`quality.coverage_ratio`) pero **no** en ninguna tabla
  v2; servirlo obligaría a abrir un fichero por empresa en cada listado.
- `intragroup_dependency` por filial en `/groups/:id` (hoy solo está el agregado
  `intragroup_dependency_max`; el detalle es la señal `A5`, que vive en `signals.csv`).
- `stats.mean_score_weighted` y `stats.mean_score_simple` en `/frames/:month`: el
  generador solo escribe `stats.mean_score`.
- `top_driver: {signal_id, value_fmt, contribution}` en las alertas (`/alerts` y
  `alerts_this_month[]` de los frames): `alerts.csv` solo trae `trigger_signal`.
- `p5` y `p95` del universo por señal en `/catalog/signals`: el `manifest.json` congela los
  21 cortes de percentil y `u_ref`, pero no p5/p95.

### Los ejemplos y las fixtures

`docs/api/examples/*.json` documentan la **forma** de cada respuesta, con el recorte de §2, y
`app/web/src/test/examples.ts` los importa como fixtures de test. Los produjo el generador del
dataset mock, que ya no está en el repositorio, así que sus valores concretos llevan
`data_kind: "mock"` en lugar de la publicación real; el contrato que describen sigue siendo el
vigente.

Regenerarlos contra la API viva exige dos cambios en `app/`: reapuntar
`app/api/scripts/gen-api-examples.mjs` a MotherDuck, y relajar el tipo de `withoutTruncated()`
en `examples.ts`, que hoy exige una clave `_truncated` que la respuesta real de `/api/v2/meta`
no trae porque no recorta ningún array.
